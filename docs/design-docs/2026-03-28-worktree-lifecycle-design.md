## Problem Statement

Five interrelated issues in the worktree and session lifecycle degrade reliability and user experience as worktree usage scales:

1. **Existing worktrees not detected** — creating a session for a branch already checked out in another worktree fails with `fatal: 'branch' is already used by worktree`. `findOrCreateWorktreeForBranch` in `watcher.ts` has correct detection logic but is never called from `POST /sessions`. The route takes `worktreePath` as input and assumes it exists.

2. **Remote branch not fetched** — creating a worktree for a PR branch that only exists on the remote fails with `fatal: invalid reference`. No `git fetch` step exists in the worktree creation path.

3. **`--continue` breaks new worktree sessions** — when "Continue" is the repo's default, new worktree sessions start then immediately close. This bug has regressed before. Root cause investigation included below.

4. **Opaque tmux session names** — `nextAgentName()` is a global counter producing `Agent 1`, `Agent 2`. Tmux sessions become `crc-Agent-1-a3b4c5d6`, which contains no repo or branch context. Running `tmux ls` gives you nothing useful.

5. **No auto-archive for merged branches** — worktrees for merged PRs persist indefinitely. `DELETE /worktrees` exists but is manual-only. `isStalePr`, `isBranchStale` exist in `git.ts`. Webhooks and `review-poller.ts` already detect PR merge events. Nothing connects them to cleanup.

## What Makes This Cool

These five items, designed as one cohesive system, become a **branch lifecycle layer** — a state machine that tracks every branch from creation through merge to cleanup. The insight: the main repo branch and worktree branches should share the same lifecycle. Worktree management (creating/deleting directories) is just an additional capability that layers on top.

This means the default repo session on `nightly` gets the same smart features (merge detection, stale branch marking, cleanup prompts) as any worktree session. A worktree session just has the extra step of managing the physical directory.

## Constraints

- Session-worktree separation just shipped (2026-03-23). Sessions are PTY processes, worktrees are git entities. This design does not reverse that.
- `server/worktree-manager.ts` does not exist. Worktree logic is split between `watcher.ts` (parsing, creation) and `index.ts` (routes, listing). This design works with the current file structure.
- Auto-archive must be prompted, not automatic. Silent deletion of worktrees with uncommitted work is dangerous.
- Must work with both tmux and non-tmux sessions.
- Must not break session restore (`restoreFromDisk`).

## Premises

1. One cohesive design doc for all 5 items — they share code paths in `watcher.ts`, `sessions.ts`, and `index.ts`.
2. Item 3 requires actual code investigation before designing a fix — the design doc includes investigation findings.
3. Work with current file structure (`watcher.ts` + `index.ts`), not a new module extraction.
4. Auto-archive should be prompted, not automatic.

## Cross-Model Perspective

Codex proposed a "workspace control plane" where `POST /sessions` no longer accepts `worktreePath` — the server owns resolution via `ensureWorkspaceForSession()`. Branches become first-class workspace entities with states (missing/fetched/active/merged/cleanup-ready).

Key insights adopted from Codex:
- **Make `--continue` explicit and state-based** — no `.claude` directory guesswork, no PTY retry magic as policy
- **Record startup/exit reason codes** — makes item 3 diagnosable instead of recurring folklore
- **Tmux names from `repoSlug + branchSlug + shortId`** — not a global counter
- **Wire merge signals into a prompt queue** — not automatic cleanup

Key insight rejected: reversing session-worktree separation. The separation just shipped and is architecturally sound. The branch lifecycle layer sits between sessions and worktrees without re-merging their concerns.

## Cross-Stream Dependencies (design/pr-integration)

The `design/pr-integration` stream is being designed in parallel. These designs share:

| Overlap | This design owns | PR integration owns | Coordination needed |
|---------|-----------------|-------------------|-------------------|
| Session creation from branch/PR | Fetch → detect → reuse-or-create flow | Open-from-picker "Create" action | Picker must call the branch lifecycle's create flow |
| PR merged state | Merge detection → cleanup prompt | PR action state machine | Share the same PR state data source, don't duplicate |
| Worktree status in picker | Detection logic (which branches have worktrees) | Picker row display (show "Open" vs "Create") | Picker reads worktree status from this design's API |
| "Has existing session" | Worktree detection WITHOUT active sessions | Session detection WITH active sessions | Both need `GET /worktrees` enriched with session info |

**This design exposes:** `POST /workspaces/worktree (existing endpoint, enhanced)` (fetch → detect → reuse-or-create) and `GET /worktrees/:path/status` (pre-cleanup checks). The PR integration stream should consume these endpoints for its picker "Create" and cleanup actions rather than implementing its own worktree creation logic.

## Architecture

```
Session (PTY process)
     |
     | attaches to a cwd
     v
Branch Lifecycle (state tracking)
 - states: active / stale / merged / archived
 - detects: PR merge events, stale branches
 - prompts: cleanup, archive
 - names: repo-scoped tmux naming
 - policy: explicit --continue decisions
     |
     | for worktree branches, also manages:
     v
Worktree Layer (optional)
 - git fetch before checkout
 - git worktree add / remove
 - .worktrees/ directory ops
 - git branch -D on cleanup

Main branch: lifecycle only (no worktree layer)
Worktree branch: lifecycle + worktree layer
```

### Branch Lifecycle States

```
                    ┌──────────┐
     create ───────>│  active  │<──── session started / new commits
                    └────┬─────┘          ^
                         │                │
              no sessions for 24h    new session started
              + 0 commits ahead      OR branch advances
                         │                │
                    ┌────v─────┐          │
                    │  stale   │──────────┘  badge in sidebar
                    └────┬─────┘
                         │
              PR merged or branch deleted upstream
                         │
                    ┌────v─────┐
                    │  merged  │──── cleanup prompt shown
                    └────┬─────┘
                         │
              user confirms cleanup
                         │
                    ┌────v─────┐
                    │ archived │──── worktree removed, branch deleted
                    └──────────┘
```

State transitions are driven by:
- **active → stale:** `isBranchStale()` returns true AND no active sessions for >24h
- **stale → active:** new session started in this branch OR branch gains new commits ahead of main
- **active/stale → merged:** new `isPrMerged()` returns true (PR state == MERGED, no delay) OR remote branch deleted. Note: `isStalePr()` has a 24h delay and is for stale cleanup, not lifecycle state. `isPrMerged()` checks merge state immediately.
- **merged → archived:** user confirms cleanup prompt (prompted, never automatic)

The main branch (e.g. `nightly`) can be `active` or `stale` but never `merged` or `archived` — you don't clean up the main worktree.

### Code Representation

Branch lifecycle state is **computed at runtime**, not persisted. On server startup and on each polling cycle, the server computes state from authoritative sources:
- `active`: has active sessions OR has recent commits (checked via `git log --since`)
- `stale`: `isBranchStale()` returns true AND no active sessions in `sessions.ts` map
- `merged`: `isStalePr()` returns true for the branch's PR

This avoids a persistence layer and ensures state is always derived from truth. The tradeoff: state doesn't survive between server restarts without recomputation, but recomputation is fast (one `git worktree list` + one PR status check per branch).

**Rate-limit handling:** Branch lifecycle state computation piggybacks on the existing `review-poller.ts` polling cycle and cached PR data. No additional GitHub API calls are needed. If the API is rate-limited, branches stay in `active` state (safe fallback). The `webhooks.ts` path (push events) is not rate-limited and provides real-time merge detection when configured.

Branch lifecycle functions live alongside existing worktree logic in `watcher.ts` (state computation) and are consumed by `index.ts` (route responses include `branchState` field) and the frontend (sidebar badges, cleanup prompts).

## Item 1: Existing Worktree Detection

### Root Cause

`findOrCreateWorktreeForBranch` in `watcher.ts:87-136` correctly checks `parseWorktreeListPorcelain` before attempting `git worktree add`. But this function is never called from the session creation path. `POST /sessions` takes `worktreePath` as a raw parameter and passes it through.

The worktree creation happens in the frontend (or a separate call), not in `POST /sessions`. If the frontend doesn't check first, it sends a worktree creation request that fails.

### Fix

The worktree creation endpoint (`POST /workspaces/worktree (existing endpoint, enhanced)` or equivalent) must call `findOrCreateWorktreeForBranch` or an equivalent check. The flow:

1. Caller requests: "I want a worktree for branch X in repo Y"
2. Server runs `git worktree list --porcelain` and parses ALL entries (including detached HEAD — current `parseWorktreeListPorcelain` filters those out)
3. If branch is already checked out:
   - In the main worktree → return `{ error: 'branch_checked_out_in_main', repoPath }` (HTTP 409). The caller (frontend) can then offer to open a repo-root session instead. Do NOT return a worktree path for the main repo, as repo-root sessions use `worktreePath: null`.
   - In a sub-worktree → return `{ path: existingWorktreePath, existing: true }`
4. If not checked out → create worktree, return `{ path: newWorktreePath, existing: false }`
5. Caller then creates a session at the returned path

### Changes needed

- `parseWorktreeListPorcelain` (`watcher.ts:69-73`): add `includeDetached?: boolean` option. Signature: `parseWorktreeListPorcelain(stdout: string, repoPath: string, opts?: { includeDetached?: boolean }): ParsedWorktreeEntry[]`. For detached HEAD entries, `branch` is set to `null` (the entry is still returned, callers check `branch !== null`). The main worktree entry always has a non-null `branch`. Only entries in `HEAD detached at <hash>` state receive `branch: null`.
- `POST /workspaces/worktree (existing endpoint, enhanced)` endpoint: the single entry point for worktree creation. Both the sidebar "new worktree" button and the open-from-picker "Create" action call this endpoint. `POST /sessions` continues to accept `worktreePath` as a pre-resolved path and does not perform worktree operations.

## Item 2: Remote Branch Fetch Before Checkout

### Root Cause

No `git fetch origin <branch>` exists anywhere in the worktree creation path. `findOrCreateWorktreeForBranch` goes straight to `git worktree add`.

### Fix

Add a fetch step before worktree creation:

1. Check if branch exists locally: `git rev-parse --verify <branch>`
2. If not found locally, fetch: `git fetch origin <branch>:<branch>` (creates local tracking branch)
3. If fetch fails (branch doesn't exist anywhere), return error
4. Proceed to worktree creation

This should be a utility function in `git.ts` (e.g., `ensureBranchLocal(repoPath, branch)`) since the open-from-picker in the PR integration stream will also need it.

**Error response on fetch failure:** `POST /workspaces/worktree (existing endpoint, enhanced)` returns `{ error: 'branch_not_found', branch, remote: 'origin' }` with HTTP 404. The frontend shows: "Branch '{branch}' not found locally or on origin."

### Edge cases

- Branch exists locally but is stale (behind remote): fetch should update, not fail
- Branch name contains `/` (e.g., `feature/foo`): git handles this natively
- Multiple remotes: default to `origin`, let config override later
- Force-pushed branches and PR-number-based fetch (`pull/<N>/head`): out of scope for MVP. `git fetch origin <branch>:<branch>` covers 95% of cases. Track as future enhancement.

## Item 3: `--continue` Breaks New Worktree Sessions

### Investigation Findings

Traced the full `--continue` decision path:

**Path 1: Normal session creation** (`index.ts:1102-1114`)
```typescript
if (explicitContinue !== undefined) {
  useContinue = explicitContinue;          // explicit override
} else if (needsBranchRename) {
  useContinue = false;                     // brand-new worktree
} else {
  useContinue = resolved.continue &&       // config default
    fs.existsSync(path.join(cwd, '.claude')); // heuristic guard
}
```

**Path 2: Session restore** (`sessions.ts:425-441`)
```typescript
// Always uses --continue args, no .claude check
args = [
  ...AGENT_CONTINUE_ARGS[s.agent],
  ...(s.claudeArgs ?? []),
  ...(s.yolo ? AGENT_YOLO_ARGS[s.agent] : []),
];
```

**Path 3: PTY quick-exit retry** (`pty-handler.ts:280-321`)
```typescript
if (canRetry && (Date.now() - spawnTime) < 3000) {
  // Strips --continue args, retries once
  let retryArgs = rawArgs.filter(a => !continueArgs.includes(a));
  attachHandlers(retryPty, false); // canRetry=false on retry
}
```

### Likely Root Cause

The `.claude` directory check (`fs.existsSync(path.join(cwd, '.claude'))`) is a flawed heuristic. `.claude/` can exist in a fresh worktree because:
- `.claude/settings.json` is committed to the repo (Claude Code convention)
- `git worktree add` checks out the branch, which includes `.claude/`
- So `fs.existsSync` returns `true` even though there's no conversation to continue

When this happens:
1. `useContinue = true` (settings say continue + `.claude/` exists)
2. Claude Code starts with `--continue`
3. No prior conversation exists in this worktree
4. Claude Code may exit quickly (behavior depends on Claude Code version)
5. PTY retry fires, strips `--continue`, retries
6. If retry also exits quickly (different reason — e.g., missing context), session dies

The retry is a one-shot safety net with `canRetry=false` on the second attempt. If the retry also fails, the session is gone.

**Why it regresses:** Any change to the worktree creation flow, `.claude/` presence, or Claude Code's `--continue` behavior can re-trigger this. The heuristic is fundamentally fragile.

### Fix

Replace the `.claude` directory heuristic with an **explicit continue policy**:

1. **New session parameter: `continuePolicy`** — `'always' | 'never'`
   - `'always'`: force `--continue` (user explicitly chose "Resume" on a stopped session)
   - `'never'`: never use `--continue` (new worktree, fresh start, or default)
   - No `'auto'` mode for MVP — the heuristic is the problem. Default to `'never'`. Future work can add auto-detection once we identify a reliable conversation state marker.
   - **Migration:** `continuePolicy` REPLACES the existing boolean `continue` field in `resolveSessionSettings` (`config.ts:131`) and `POST /sessions` request body (`index.ts:1020`). The old `.claude` directory heuristic in `index.ts:1102-1114` is removed entirely. The config field `continue: true/false` is mapped to `continuePolicy: 'always'/'never'` during config resolution for backward compatibility.

3. **Worktree creation sets `continuePolicy: 'never'`** — the frontend passes this when creating a session for a newly-created worktree. Eliminates the heuristic entirely for the new-worktree case.

4. **Session restore keeps `--continue`** — the restore path is correct (the session DID have a prior conversation). No change needed there.

5. **Exit reason codes:** When a PTY exits within 3 seconds, log the exit code and any stderr to the session metadata. This makes future regressions diagnosable: "session exited with code 1 after 1.2s, stderr: 'no conversation to continue'".

**PTY retry mechanism:** The existing quick-exit retry (`pty-handler.ts:280-321`) is preserved unchanged. With `continuePolicy: 'never'` on new worktrees, the retry should never be needed for the `--continue` failure case. The retry remains as a fallback for other unexpected quick exits (binary not found, permission errors, etc.).

### Why this won't regress

The fix eliminates the heuristic at the decision point. Instead of inferring intent from filesystem state, the caller states intent explicitly. There is no "auto" path that could silently re-break when `.claude/` contents change.

## Item 4: Repo-Scoped Tmux Naming

### Current State

```typescript
// sessions.ts:292-294
function nextAgentName(): string {
  return `Agent ${++agentCounter}`;
}

// pty-handler.ts:17-20 (generateTmuxSessionName)
// Produces: crc-Agent-1-a3b4c5d6
```

`agentCounter` is global. Running `tmux ls` shows:
```
crc-Agent-1-a3b4c5d6: ...
crc-Agent-2-b4c5d6e7: ...
crc-Agent-3-c5d6e7f8: ...
```

No way to tell which repo or branch each session belongs to.

### Fix

**New tmux naming format:** `crc-{repoSlug}-{branchSlug}-{shortId}`

Examples:
```
crc-claude-remote-cli-nightly-a3b4c5d6
crc-claude-remote-cli-fix-auth-b4c5d6e7
crc-myapp-main-c5d6e7f8
```

**Implementation:**
The tmux name is computed in `pty-handler.ts:generateTmuxSessionName`, which already accepts `displayName` and `id`. Change what's passed as `displayName`:
1. In `index.ts`, before calling `sessions.create()`, compute `tmuxDisplayName = repoName + '-' + branchSlug`. Derive `repoName` from `path.basename(workspacePath)`, the same workspace root path already present in the route handler (variable `name` at line ~1149 in `index.ts`). `branchSlug` is sanitized from `branchName`.
2. Pass `tmuxDisplayName` as a new field to `createPtySession` for tmux naming
3. Keep `nextAgentName()` for the UI `displayName` (sidebar still shows "Agent 1") — the tmux session name and UI display name are now independent
4. `branchSlug`: call `git.branchToDisplayName()` (already strips `feature/`, `fix/` prefixes in `git.ts:419-424`) then sanitize for tmux (replace non-alphanum with `-`, truncate to 30 chars)

**Future enhancement: per-repo agent counter.** Replace global `agentCounter` with a per-workspace counter. Lower priority — deferred to a future iteration.

## Item 5: Auto-Archive Merged Branches

### Flow

```
PR merge detected (webhook or poller)
          │
          v
Mark branch state: merged
Show "merged" badge in sidebar
          │
          v
Show cleanup prompt (non-blocking notification in sidebar)
"PR #42 merged. Clean up worktree and branch?"
  [Clean up]  [Keep]  [Dismiss]
          │
          v
User clicks "Clean up"
          │
          v
Pre-cascade checks (frontend gathers state before prompting):
  1. Check for active sessions → include in prompt if found
  2. Check for uncommitted changes (git status --porcelain) → include in prompt if found
  3. Show single confirmation: "Clean up worktree? [N active sessions will be closed] [Uncommitted changes will be lost]"
  4. If user declines at any point, entire cascade is aborted — no partial state

Cascade (all-or-nothing after user confirms):
  1. Kill any active sessions in the worktree
  2. git worktree remove --force <path> (--force is safe here because the user already confirmed the uncommitted changes warning)
  3. git worktree prune
  4. git branch -D <branch>
  5. Emit worktrees-changed event
  6. Remove worktree metadata
```

### Detection sources

Already exist:
- `server/webhooks.ts` — receives GitHub webhook events (PR merged)
- `server/review-poller.ts` — polls PR status periodically
- `git.ts:isStalePr()` — returns true if PR is merged/closed >1 day ago
- `git.ts:isBranchStale()` — checks if branch has 0 commits ahead of main

**New:** Instead of adding a new `branch-state-changed` WebSocket event, enrich the existing `GET /worktrees` response with a `branchState: 'active' | 'stale' | 'merged'` field per worktree entry. The frontend already calls `GET /worktrees` and refreshes on `worktrees-changed` events. When a merge event fires (webhook or poller), broadcast the existing `worktrees-changed` event to trigger a refresh, which will include the updated `branchState`. This avoids introducing a new event type and keeps the data flow through the existing refresh model.

For each worktree in the `GET /worktrees` response, compute `branchState` using `isPrMerged()` (new function, checks PR state == MERGED immediately) and `isBranchStale()`. Include `prNumber` and `prTitle` when state is `merged`.

**Multi-client race:** If multiple clients are connected, only the first confirmed cleanup cascade executes. The current `DELETE /worktrees` returns 400 for already-removed paths. **Fix needed:** Change validation to return 404 when the worktree path no longer exists in `git worktree list` output, so the second client sees "already cleaned up" rather than a validation error. No cross-client lock needed.

### Cleanup cascade details

The `DELETE /worktrees` endpoint already handles most of the cascade. It needs two additions:
1. **Pre-flight check endpoint:** New `GET /worktrees/:path/status` returns `{ activeSessions: string[], hasUncommittedChanges: boolean }`. The frontend calls this before showing the cleanup prompt, so the prompt includes all relevant warnings upfront.
2. **Force flag on delete:** `DELETE /worktrees` accepts `{ force: true }` to bypass the current 409 on active sessions. The frontend only sends `force: true` after the user confirms the pre-cascade prompt.

The webhook/poller merge event integration: add a lifecycle state update call in the PR merged handler in `webhooks.ts` (the `pull_request.closed` event where `merged === true`) and in `review-poller.ts` (where `isStalePr()` transitions are detected). Both call a shared `onBranchMerged(repoPath, branch)` function in `watcher.ts` that broadcasts `branch-state-changed` to connected clients.

### Main branch behavior

The main branch can be marked `stale` (no recent commits) but never `merged` or `archived`. The cleanup cascade does not apply. The sidebar can show a "stale" indicator but no cleanup prompt.

## Approaches Considered

### Approach A: Five Independent Fixes
Fix each item separately with minimal code changes. No unifying lifecycle concept. Main branch doesn't participate. Effort: S. Risk: Low. Completeness: 7/10.

### Approach B: Pragmatic Lifecycle
All fixes plus merge detection → cleanup prompts. But lifecycle only applies to worktree branches, not the main branch. Effort: M. Risk: Med. Completeness: 8/10.

### Approach B' (CHOSEN): Branch Lifecycle Layer
Universal branch lifecycle that applies to all branches. Worktree management layers on top. Session-worktree separation preserved. Effort: M. Risk: Med. Completeness: 9/10.

### Approach C: Workspace Control Plane (Codex-inspired)
Branches become first-class entities. `POST /sessions` takes branch target, server resolves everything. Partially reverses session-worktree separation. Effort: L-XL. Risk: High. Completeness: 10/10.

## Recommended Approach

**B' — Branch Lifecycle Layer.** Captures the architectural insight that branch lifecycle is universal, worktree management is a layer. Fixes all 5 items. Keeps session-worktree separation intact. Medium effort, medium risk.

The key architectural decision: the lifecycle layer doesn't own sessions or worktrees — it provides state tracking and event coordination that both can consume. Sessions query it for `--continue` policy. The frontend queries it for badges and cleanup prompts. The worktree creation flow queries it for detection and fetch.
