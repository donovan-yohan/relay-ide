# Design: True Workspaces — Multi-Repo Workspace Grouping

## Problem Statement

claude-remote-cli treats each repository/directory as a "workspace." For developers working across multiple repos (frontend + backend + shared libs), this means:
- Each repo is a separate sidebar entry with no visual or logical grouping
- Launching a Claude session scopes it to a single repo — no cross-repo awareness
- `--add-dir` exists in Claude Code but requires manual specification every time
- No persistent configuration for "these repos belong together"

**Current state of the infrastructure:** The config already has `repos: string[]` as the primary field (with `workspaces?: string[]` as a legacy alias). `workspaceGroups: Record<string, string[]>` exists, validates on load (one-group-per-repo), but has no UI for managing groups. The frontend already has `workspaces = $state<Workspace[]>([])` and `fetchWorkspaces()` wired up in `sessions.svelte.ts`, but the current `Workspace` type is just `{ path, name, isGitRepo, defaultBranch }` — a repo descriptor, not a grouping entity. The plumbing exists but serves the wrong abstraction.

## What Makes This Cool

One click, fullstack mode. You define a workspace called "My App" containing your frontend, backend, and shared-libs repos. Hit "launch workspace session" and Claude starts with all three repos in context via `--add-dir`. It sees the API endpoint in your backend and the `fetch()` call in your frontend simultaneously. From your phone.

This combination — remote access + AI sessions + multi-repo grouping — doesn't exist in any other tool. Zencoder does multi-repo indexing but not remote sessions. Code-server does browser delivery but not AI-native orchestration. This is genuinely new territory.

## Constraints

1. **npm package** — ships via `npm publish`, no new distribution channel needed
2. **Invisible migration** — existing single-repo users must never notice the transition
3. **`workspaceGroups` is the foundation** — evolve, don't replace
4. **Session-worktree separation is shipped** — sessions already have `workspacePath` + `worktreePath`, so workspace-scoped sessions need a clear relationship model
5. **DESIGN.md governs all visual decisions** — pure black, monospace, zero border-radius, outline-only buttons, workspace borders from `Workspace Grouping` section
6. **Incremental delivery** — each merged PR should be independently usable
7. **No breaking config changes** — v3→v4 migration must handle all existing fields

## Premises

1. The rename (workspace → repo) is necessary, not cosmetic — keeping "workspace" for both concepts creates genuine confusion in the codebase and UI
2. `workspaceGroups` is the right foundation — evolve into a full Workspace entity rather than creating a new concept from scratch
3. The fullstack session (`--add-dir` with all workspace repos) is the primary UX payoff — grouping and view modes are supporting features
4. Migration must be invisible — existing single-repo users see their repos in an "ungrouped" section automatically
5. Workspace templates belong in scope, not as a future stretch goal

## Cross-Model Perspective

Codex (independent cold read) proposed "workspace = project topology" — not just a bag of repos, but a graph of relationships with repo roles (frontend/backend/lib), dependency edges, and coordinated change sets. Key insights:

- The emotional center is "collapsing cross-repo cognitive load into one action"
- The killer extension is cross-repo change sets: one prompt, multiple repos, coordinated worktrees/branches/PRs
- Weekend build strategy: collapse rename + model + launch + migration into one vertical slice
- Code-server is the closest delivery analogy (browser-hosted dev), but the AI session orchestration layer is entirely new

## Data Model

### Workspace Entity (new)

```typescript
interface Workspace {
  id: string;                  // UUID, stable across renames
  name: string;                // User-visible name ("My Fullstack App")
  repos: string[];             // Ordered list of repo paths (absolute); array order = display order within workspace
                               // Many-to-many: a repo can belong to multiple workspaces
  themeColor?: string;         // From workspace-theme-color design doc
  order: number;               // Display ordering among workspaces
  template?: WorkspaceTemplate;
  settings?: WorkspaceLevelSettings; // Subset of WorkspaceSettings (excludes repo-scoped fields)
                                     // Cascade: global → workspace.settings → repoSettings[path] → session
}

interface WorkspaceTemplate {
  repoRoles?: Record<string, RepoRole>; // path → role
  defaultAgent?: string;
  customPrompt?: string;
  claudeArgs?: string[];       // Additional args for workspace sessions
}

type RepoRole = 'frontend' | 'backend' | 'lib' | 'infra' | 'docs' | 'other';
```

### Repo Entity (renamed from current Workspace)

```typescript
interface Repo {
  path: string;                // Absolute filesystem path
  name: string;                // Display name (basename or custom)
  isGitRepo: boolean;
  defaultBranch: string | null;
}
```

### Config v4

The current config already uses `repos: string[]` as the primary repo list and `workspaceSettings` for per-repo overrides. The `workspaces?: string[]` field is a legacy alias that some older configs still have. The migration reconciles this.

```typescript
interface Config {
  configVersion: 4;            // NEW field (no version field exists today)
  repos: string[];             // Already exists — no rename needed
  repoSettings: Record<string, RepoSettings>; // Renamed from workspaceSettings
  workspaces: Workspace[];     // NEW: workspace entities (replaces workspaceGroups)
  // Removed: workspaceGroups (promoted to workspaces[])
  // Removed: legacy workspaces?: string[] alias (absorbed into repos[])
  // ... global defaults unchanged
}
```

### Session Changes

```typescript
interface BaseSession {
  // Existing fields
  repoPath: string;            // Renamed from workspacePath
  worktreePath: string | null;
  cwd: string;

  // New field
  workspaceId?: string;        // Set when launched as a workspace session
  additionalDirs?: string[];   // The --add-dir paths used for this session
}
```

### Settings Cascade

```
Global defaults → Workspace.settings → repoSettings[path] → Session overrides
```

`Workspace.settings` uses a **subset** of the existing `WorkspaceSettings` type: session defaults (`defaultAgent`, `defaultContinue`, `defaultYolo`, `launchInTmux`, `claudeArgs`) and custom prompts (`promptGeneral`, etc.). Repo-scoped fields that don't make sense at workspace level (`webhookId`, `webhookEnabled`, `webhookError`, `nextMountainIndex`, `defaultBranch`, `remote`, `branchPrefix`) are excluded. Define a `WorkspaceLevelSettings` type that picks only the relevant fields.

Per-repo `repoSettings[path]` overrides workspace. Session-specific overrides (from launch args) override everything.

**Single-repo sessions do NOT inherit workspace settings.** When a repo belongs to multiple workspaces, there's no deterministic way to pick which workspace's settings apply. Workspace settings cascade only for workspace sessions (launched via `POST /workspace-groups/:id/session`). Single-repo sessions use: `global → repoSettings[path] → session`.

**Implementation change required:** `resolveSessionSettings()` in `config.ts` gets a new optional `workspaceId` parameter. Only `POST /workspace-groups/:id/session` passes it. When present, workspace-level settings are inserted between global defaults and session overrides. The existing `POST /sessions` endpoint does not pass `workspaceId`.

## Migration Strategy (pre-v4 → v4)

Runs automatically on config load. Fully backwards-compatible. Note: no `configVersion` field exists in current configs, so absence of the field triggers migration.

1. **Detect version:** If `configVersion` is missing or `< 4`, run migration
2. **Reconcile repo arrays:**
   - `config.repos` already exists as the primary repo list for most users
   - If `config.workspaces` (the legacy `string[]` alias) exists and `config.repos` does not, copy `config.workspaces` → `config.repos`
   - If both exist, merge (union, preserving `repos` order), then delete the legacy `config.workspaces` string array
3. **Rename settings:**
   - `config.workspaceSettings` → `config.repoSettings` (same type, just renamed key)
4. **Promote groups:** If `config.workspaceGroups` exists, convert each group into a `Workspace` entity:
   ```
   workspaceGroups: { "infra": ["/path/a", "/path/b"] }
   →
   workspaces: [{ id: uuid(), name: "infra", repos: ["/path/a", "/path/b"], order: 0 }]
   ```
   Then delete `config.workspaceGroups`.
5. **Ungrouped repos:** Repos not in any workspace remain in `config.repos` but are NOT auto-assigned to a "Default" workspace. They appear in the "ungrouped" sidebar section.
6. **Session compat:** `pending-sessions.json` v3 fields (`workspacePath`) undergo a one-shot transform on first v4 load: read `workspacePath`, write as `repoPath`, delete old field. No permanent dual-field shim — the file is rewritten with v4 field names on restore. Format bumped to v4.
7. **Validator update:** The `loadConfig()` `workspaceGroups` validator currently references `config.workspaces` (the old `string[]` alias) and enforces one-group-per-repo. Two changes: (a) update to reference `config.repos` instead of the legacy alias, (b) drop the one-group-per-repo constraint — v4 workspaces support many-to-many (a repo can belong to multiple workspaces). Run repo array reconciliation (step 2) before groups promotion (step 4).
8. **localStorage compat:** `collapsedWorkspaces` (Set of path strings) and `activeWorkspacePath` in localStorage are cleared on first v4 load. Collapse state resets — acceptable for a UI-only state that rebuilds naturally.
9. **Set version:** `config.configVersion = 4`

No "Default" workspace is created. Ungrouped is a UI concept, not a data model entity.

## API Changes

### Existing Endpoints (unchanged for v1)

All existing `/workspaces/*` routes stay as-is. The full `/workspaces → /repos` route rename is a documented follow-up task (after v1 is confirmed working). The existing router has 20+ endpoints (dashboard, settings, PR, CI, branch ops, browse, etc.) that all live under `/workspaces`. Renaming them all is a separate effort.

### New Endpoints (workspace grouping CRUD at `/workspace-groups`)

| Endpoint | Method | Body | Description |
|----------|--------|------|-------------|
| `/workspace-groups` | `GET` | — | List all workspace groups. Returns `Workspace[]` |
| `/workspace-groups` | `POST` | `{ name, repos, themeColor? }` | Create workspace group |
| `/workspace-groups/:id` | `PUT` | `Partial<Workspace>` (including full `repos[]` for reordering repos within) | Update workspace |
| `/workspace-groups/:id` | `DELETE` | — | Delete workspace (repos remain ungrouped) |
| `/workspace-groups/reorder` | `PUT` | `{ ids: string[] }` | Reorder workspaces |
| `/workspace-groups/:id/session` | `POST` | Session creation opts | Launch workspace session (auto `--add-dir` with worktrees) |

Repo reordering within a workspace is done via `PUT /workspace-groups/:id` with a full `repos[]` array in the body.

**Follow-up task:** After v1 ships and is confirmed working, rename all existing `/workspaces/*` routes to `/repos/*` and move workspace grouping from `/workspace-groups` to `/workspaces`. Document all callsites and differences between legacy workspace (repo) and new workspace (group) concepts.

### Workspace Session Launch

`POST /workspace-groups/:id/session` does:
1. Look up workspace by ID, get `repos[]`
2. For each repo in parallel (`Promise.all`):
   - If git repo: find existing workspace worktree or create one lazily (`git worktree add` on the repo's default branch)
   - If not git repo: use the directory path directly
   - On individual repo failure: mark as failed, don't block other repos
3. If ALL repos failed: return error, clean up any worktrees created
4. If SOME repos failed: proceed with the successful ones (best-effort degraded launch). Toast error listing which repos failed
5. First successful repo's resolved path = `cwd`, remaining = `--add-dir` args
6. Apply workspace-level settings cascade (`global → workspace.settings → session`)
7. Spawn PTY with combined args
8. Set `session.workspaceId = workspace.id`
9. Set `session.additionalDirs = resolvedPaths.slice(1)`

**Why worktrees:** Workspace sessions must not compete with work happening directly on repo root directories. Worktrees are created lazily on first launch (not on workspace creation), so workspace creation is pure config with no filesystem side effects.

**Branch policy:** Workspace worktrees use each repo's configured default branch. Coordinated feature branches (same branch name across all repos) are a follow-up feature.

**Session persistence:** `pending-sessions.json` format v4 must include `workspaceId` and `additionalDirs` fields so workspace sessions survive server restarts with full multi-repo context.

### Frontend State Changes

In `sessions.svelte.ts`, the existing `workspaces = $state<Workspace[]>([])` (which currently holds repo descriptors) undergoes a full type change:
- `workspaces: Workspace[]` (old type: `{ path, name, isGitRepo, defaultBranch }`) becomes `repos: Repo[]` (same shape, renamed type)
- A new `workspaces: Workspace[]` state is added using the new grouping entity type (`{ id, name, repos[], settings, ... }`)
- `refreshAll()` fetches repos (from `GET /repos`), workspaces (from `GET /workspaces`), sessions, and worktrees
- Add `getReposForWorkspace(workspaceId)` helper
- Replace existing `getSessionsForWorkspace(workspacePath: string)` (which filters by `s.workspacePath === path`) with `getSessionsForWorkspace(workspaceId: string)` — entirely new contract: returns sessions where `s.workspaceId === workspaceId` (workspace sessions) OR `s.repoPath` is in the workspace's `repos[]` (single-repo sessions within this workspace)

In `ui.svelte.ts`:
- `activeWorkspacePath` → `activeRepoPath` (tracks selected repo)
- Add `activeWorkspaceId` (tracks selected workspace group)
- `collapsedWorkspaces` Set keys change from paths to workspace IDs

### Sidebar Changes

**Architecture:** Workspace-organized navigation is the default and permanent sidebar shell. No view mode toggle in v1 — the sidebar always shows workspaces with nested repos, plus an ungrouped section. View modes are a follow-up feature.

**Collapse behavior:** Tree-style, each workspace independent, all collapsed by default. Users expand the workspace they're working in. Multiple can be open simultaneously.

**Visual treatment:**
- **Collapsed workspace:** Single row with colored left-edge accent (2px, `color-mix(in srgb, [theme-color] 30%, transparent)`), workspace name in user-defined casing (`--font-size-sm`, `--text`), session count inline (`--font-size-xs`, `--text-muted`, format: `N sessions`)
- **Expanded workspace:** Full rectangular outline border per DESIGN.md Workspace Grouping section (`1px solid color-mix(in srgb, [theme-color] 30%, transparent)`), pure black interior. Contains nested `RepoItem` components and the launch button
- **Launch button:** Primary variant (accent/terracotta), TuiButton with box-drawing corners, full-width within expanded workspace container, placed after workspace-level sessions and before repo list. Label: `> launch workspace session`
- **Workspace session badge:** `--color-orange` (`#fb923c`), outline-only, zero border-radius, lowercase `workspace`, `--font-size-xs` (0.75rem)
- **Ungrouped section:** Flat repo list below workspaces, no container border. Section label `ungrouped` in `--text-muted`, `--font-size-xs`. Hidden when all repos are grouped.

**Empty states:**
- **No workspaces created:** Ungrouped repos appear with muted prompt `no workspaces yet` + ghost button `[ + new workspace ]` above repo list
- **Workspace with no repos:** Inside expanded container: `no repos` in `--text-muted`, `--font-size-xs`
- **First load:** Cipher-decode loading effect on workspace names until data resolves

**Loading/error states for launch:**
- Button shows braille spinner (`⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`) while creating worktrees
- On error: toast in `--status-error` with `workspace session failed: [reason]`
- On partial failure (some repos missing from disk): toast with error details, offer to launch with remaining valid repos

**Workspace management:** All CRUD (create, edit name/repos/color, delete) lives in a dedicated "workspaces" section within the existing settings dialog. Not inline in the sidebar. The sidebar is view-only for workspaces.

## Open Questions

1. **Repo ordering within a workspace:** Does each workspace maintain its own repo order, or does the global `repos[]` order apply?
   - **Recommendation:** Workspace-local ordering via `workspace.repos[]` array order. Global `repos[]` order only affects ungrouped repos.

2. **Workspace session display:** Does a workspace session appear under the workspace header, under each repo, or both?
   - **Recommendation:** Under the workspace header only, with a `workspace` badge. Not duplicated under individual repos.

3. **Which repo is primary?** When launching a workspace session, the first repo in `workspace.repos[]` becomes `cwd`. Should this be configurable or is array order sufficient?
   - **Recommendation:** Array order is sufficient. Users can reorder repos within a workspace.

4. **Workspace-level worktrees:** ~~Not in v1.~~ **Now in v1 scope.** Each workspace has a default worktree set (one worktree per repo, always present). Additional workspace worktrees create coordinated checkouts across all repos. Naming convention TBD (likely `ws-<workspace-name>-<identifier>`).

5. **Template sharing:** Can workspace templates be exported/imported?
   - **Recommendation:** Not in v1. Templates are per-config. Export/import is a natural follow-up.
