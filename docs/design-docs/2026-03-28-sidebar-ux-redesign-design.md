## Problem Statement

The Relay sidebar is the primary navigation surface for managing Claude Code sessions across repos and worktrees. Six independent issues make it unreliable and hard to scan:

1. No double-click to expand/collapse workspace rows
2. Branch names go stale when the agent switches branches mid-session
3. Inactive repos show "default" name and "master" branch instead of real git state
4. Status indicators (colored dots + count badges) don't distinguish session states at a glance
5. PR status is a tiny colored dot with no shape distinction between draft/open/review/approved/merged/closed
6. Sidebar header ("Relay" + collapse icon) wastes space and doesn't read as a home button

The root cause is that the sidebar was designed as a static list, not a live dashboard. It shows stale data, uses a single visual channel (color) for all state, and makes no distinction between "needs your attention now" and "working in the background."

## What Makes This Cool

The sidebar becomes an attention engine. Three independent visual axes compose freely to tell you everything at a glance: what the session IS (shape+color), whether you've SEEN the latest change (bold+pulse), and what's happening with the PR (icon+color). Motion is reserved exclusively for actionable items, so your eye is drawn to what needs you, not what's just running. The shape language (circle -> triangle -> diamond -> square -> dash) maps organic-to-angular onto calm-to-urgent. And it all works with any agent (Claude Code, Codex, Gemini) through a generic `AgentState` interface.

## Constraints

- Must use existing TUI primitives (StatusDot, CipherText, MarqueeText, TuiTooltip) from the shipped design system overhaul
- Must respect DESIGN.md visual system (all lowercase, monospace, box-drawing, no emoji)
- Color palette: green `--status-success` (#4ade80, at 0.4-0.8 opacity for running), yellow `#f0c674` (warning/idle), red `#cc6666` (action needed), gray `#333-#555` (inactive)
- Sidebar header redesign defers to the Phase 3 spotlight design doc (`2026-03-23-relay-phase3-spotlight-identity-design.md`)
- Generic `AgentState` interface, not Claude Code-specific
- Must work on mobile (narrow sidebar, touch targets)

## Premises

1. All 6 items belong in one design doc and one implementation stream, since they share the sidebar surface and the indicator system touches all of them.
2. `BranchWatcher` in `server/watcher.ts` already watches `.git/HEAD` per repo/worktree. The plumbing exists; the gap is connecting it to WebSocket events and propagating to the frontend.
3. Sidebar header redesign defers to Phase 3 spotlight design doc rather than re-deciding here.
4. An "attention engine" means sorted sidebar (reordering by urgency), not just better indicators. Workspaces and sessions re-sort by computed attention score.
5. Existing TUI primitives (CipherText, StatusDot, MarqueeText, TuiTooltip) are reused. This doc specifies WHERE they appear, not HOW they work internally.

## Design System: Three-Axis Indicator Model

### Axis 1: Session State (Shape + Color)

Shape language maps organic-to-angular onto calm-to-urgent:

```
 circle     triangle    diamond    hollow-diamond   square     dash
   ●           ▶           ◆            ◇             ■         ─
 flowing     alert      action      question       error      off
```

| State | Shape | Color | Size | Description |
|-------|-------|-------|------|-------------|
| initializing | ● circle | green `--status-success` (#4ade80) | 10px, 0.4 opacity | agent starting up (identical to running but lower opacity — "warming up") |
| running | ● circle | green `--status-success` (#4ade80) | 10px, 0.8 opacity | agent is actively generating output |
| idle | ▶ triangle | yellow `#f0c674` | 10px | agent has paused, not waiting for input |
| needs-approval | ◆ diamond (filled) | red `#cc6666` | 14px, bold | agent is blocked on tool approval |
| needs-answer | ◇ diamond (hollow) | red `#cc6666` | 14px | agent asked a question, waiting for response |
| error | ■ square | red `#cc6666` | 12px | agent crashed or encountered a fatal error |
| inactive | ─ dash | gray `#333` | 10px | session has exited |

Note: minimum indicator size is 10px to avoid browser minimum font-size issues on mobile. Size differentiation is achieved through font-weight (bold for actionable) and the surrounding treatments (bold name, accent border) rather than sub-10px sizing. Indicators must be rendered as text characters (not SVG) for the color-alpha pulse to work as specified. If color-alpha pulse has mobile rendering issues, an acceptable fallback is animating `text-shadow` alpha instead of `color` alpha. Verify the project's monospace font includes ⊘ (U+2298) and ◌ (U+25CC); if not, substitute with characters from the Box Drawing block.

Design rationale:
- **Shape encodes urgency.** Circles are organic (flowing water), triangles are angular (yield sign), diamonds are sharp (attention), squares are blocky (full stop). Even without color, you can tell what needs you.
- **Color is stoplight.** Green = going. Yellow = look. Red = act. Gray = off. Everyone already knows this language.
- **Size reinforces hierarchy.** Running is tiny (leave it alone). Actionable is large and bold (look at me). Inactive barely exists.
- **Red is notification red**, not error red. Like a messenger badge. "Hey look at me." The square shape is the one that actually means something broke.

### Axis 2: Read/Unread (Independent Overlay)

Inspired by email inbox UX. Read/unread is orthogonal to session state. Any state can be unread.

| Read Status | Name Treatment | Indicator Treatment | Border |
|-------------|---------------|-------------------|--------|
| unread | **bold, bright white** `#e8e8e8` | pulse animation on indicator | left accent border (color matches state) |
| read | normal weight, muted `#999` | static indicator | no border |

**Pulse animation uses color alpha, NOT opacity.** This prevents tooltips and child elements from fading with the indicator. Red pulses fast (1.4s), yellow pulses slow (2.5s).

```css
/* correct: animate color channel */
@keyframes pulse-red {
  0%, 100% { color: rgba(204,102,102,1); }
  50% { color: rgba(204,102,102,0.15); }
}
/* wrong: animate opacity — cascades to tooltips */
@keyframes pulse-bad {
  0%, 100% { opacity: 1; }
  50% { opacity: 0.2; }
}
```

**When does unread trigger?**
- Session transitions from running to any non-running state AND user is not currently viewing it
- Session receives new output while user is viewing a different session
- PR status changes (new review, approval, merge)
- Error occurs

**When does unread clear?**
- User clicks into the session (views terminal output)
- If the user is already viewing the session, new output does NOT trigger unread (they're watching it live)
- Switching away from a session and switching back clears any unread that accumulated while away

### Axis 3: PR Status (Icon + Color, No Text)

Replace text labels with recognizable icons (GitHub-style). Bolder, more saturated colors than current dots.

| PR State | Icon | Color | Tooltip |
|----------|------|-------|---------|
| draft | ◌ (dotted circle) | gray `#555` | "draft pr" |
| open | ○ (open circle) | blue `#4a9eff` | "open pr" |
| review-requested | ○ (open circle) | yellow `#f0c674` | "review requested" |
| changes-requested | ✕ (cross) | red `#e05252` | "changes requested" |
| approved | ✓ (checkmark) | green `#5cb85c` | "approved" |
| merged | ● (filled circle) | purple `#b294bb` | "merged" |
| closed | ⊘ (slashed circle) | red `#e05252` | "closed (not merged)" |

Note: `closed` uses ⊘ (not ✕) to distinguish from `changes-requested` by shape alone.

**Comment count badge:** Small `[3]` badge in muted style appears when the PR has unread comments. Requires GitHub webhook integration to fetch efficiently. If webhook data is unavailable, omit the badge (graceful degradation).

### Text Effects

- **MarqueeText** for overflow: When session name or branch name exceeds available width, the text scrolls horizontally on hover. Uses the existing `MarqueeText` TUI primitive.
- **CipherText decode** on branch change: When `BranchWatcher` fires a branch-changed event, the branch name in the secondary line animates through random characters before resolving to the new branch name. Uses the existing `CipherText` primitive.

### Discoverability: Tooltips

Every indicator (session state, PR status) has a tooltip on hover explaining its meaning. Uses the existing `TuiTooltip` primitive. This lets new users learn the shape/color language without documentation.

## Sidebar-Level Interaction States

| Scenario | User sees | Behavior |
|----------|-----------|----------|
| **Sidebar first load** | CipherText noise resolving into workspace names (one per workspace, ~300ms stagger). Session rows appear as data arrives. No CLS because sort order is computed after all data loads, not incrementally. | Use CipherText as loading state for workspace names. Show `+ add workspace` footer immediately (it's static). |
| **Empty workspace** | Workspace header with name, no pips (pip section hidden when count is 0). Single `+ new worktree` row below. | No "no sessions" text. The `+ new worktree` CTA is the empty state. |
| **State transition** | Indicator shape snaps instantly (no morph). Color cross-fades over 150ms. If transitioning TO an unread state, the bold name treatment fades in over 200ms and pulse starts. If transitioning FROM unread (user viewed), bold fades out over 300ms. | Snap shape, fade color. Shape morphing (circle → diamond) looks janky at 10-14px. Instant swap is cleaner. |
| **WebSocket disconnect** | After 5s of failed pings, show a subtle `disconnected` indicator in the sidebar header (dim red dot next to "relay"). All session indicators freeze but remain visible. On reconnect, trigger `refreshAll()` which recomputes all states. | Existing ping/pong mechanism handles detection. The frozen-indicator problem is solved by the reconnect refresh. |

## Session State Machine

```
                    ┌──────────┐
                    │initializing│
                    └─────┬──────┘
                          │ pty connected
                          ▼
              ┌─────── running ◄────────────┐
              │           │                  │
              │     idle (no output          │ user provides
              │      for N seconds)          │ input/approval
              │           │                  │
              │           ▼                  │
              │    ┌─── idle ───┐            │
              │    │            │            │
              │  output     agent asks       │
              │  resumes    question         │
              │    │            │            │
              │    ▼            ▼            │
              │  running   needs-answer ─────┘
              │               │
              │          agent requests
              │          tool approval
              │               │
              │               ▼
              │         needs-approval ──────┘
              │
              │  pty exits / agent crashes
              │           │        │
              │           ▼        ▼
              │       inactive   error
              └──────────────────────┘
```

**BackendDisplayState** (from server, over WebSocket):
`initializing | running | idle | permission`

**AgentState** (generic, agent-agnostic):
`initializing | waiting-for-input | processing | permission-prompt | error | idle`

**DisplayState** (frontend, with read/unread tracking):
`initializing | running | unseen-idle | seen-idle | permission | needs-answer | inactive | error`

The frontend maps BackendDisplayState + read/unread tracking into DisplayState. The three-axis indicator model then maps DisplayState into visual presentation.

**State mapping chain:**

| BackendDisplayState | AgentState | DisplayState | Visual (Axis 1) |
|-------|-------|-------|-------|
| `initializing` | `initializing` | `initializing` | ● green circle |
| `running` | `processing` | `running` | ● green circle |
| `idle` | `idle` | `unseen-idle` or `seen-idle` | ▶ yellow triangle |
| `permission` | `permission-prompt` | `permission` | ◆ red diamond |
| `permission` | `waiting-for-input` | `needs-answer` | ◇ red hollow diamond |
| (pty exit) | — | `inactive` | ─ gray dash |
| (pty crash) | `error` | `error` | ■ red square |

**Detecting `waiting-for-input` vs `permission-prompt`:** Claude Code distinguishes these via the `requiresApproval` flag (tool approval) vs the `AskUserQuestion` tool (agent asking a question). The backend maps both to `permission` BackendDisplayState. To distinguish them on the frontend, extend the WebSocket event to include a `permissionType: 'approval' | 'question'` field. Other agents (Codex, Gemini) map their own blocking states to the same two categories.

## Attention Score & Sorting

Each session computes an `attentionScore` based on:

```typescript
function computeAttentionScore(session: SidebarSession): number {
  let score = 0;

  // state urgency (highest weight)
  switch (session.displayState) {
    case 'permission':    score += 1000; break;
    case 'needs-answer':  score += 900;  break;
    case 'error':         score += 800;  break;
    case 'unseen-idle':   score += 500;  break;
    case 'running':       score += 100;  break;
    case 'seen-idle':     score += 10;   break;
    case 'inactive':      score += 1;    break;
  }

  // pr urgency
  if (session.prStatus === 'changes-requested') score += 200;
  if (session.prStatus === 'review-requested')  score += 150;

  // recency
  score += Math.max(0, 100 - minutesSinceLastActivity(session));

  // unread bonus (note: unseen-idle already implies isUnread=true,
  // so these stack intentionally — an unseen-idle session scores
  // 500 + 300 = 800, tying with error at 800. recency breaks the tie.)
  if (session.isUnread) score += 300;

  return score;
}
```

**Workspace sorting:** Workspaces sort by their highest-scoring session. A workspace with a permission-needed session sorts above one with only running sessions.

**Session sorting within workspace:** Sessions sort by attentionScore descending within their workspace.

**User override (Phase 2, deferred):** Users could pin workspace order via drag-and-drop. Pinned workspaces would maintain their position while unpinned ones sort by attention. Deferred because it requires new interaction model, persistence, and state management beyond the scope of these 6 items. For Phase 1, workspaces always sort by attention score.

## Item-by-Item Design Decisions

### Item 1: Double-click to expand/collapse

Add `dblclick` handler on the full workspace row in `WorkspaceItem.svelte`. Distinguish from single-click (navigate to session) using a 200ms delay on single-click. Single-click navigation is intentionally delayed 200ms to allow double-click detection, which is a known UX trade-off (acceptable because workspace collapse is a frequent action and 200ms is below perceptible delay threshold).

Implementation: `frontend/src/components/WorkspaceItem.svelte`

### Item 2: Stale branch names (active sessions)

`BranchWatcher` already watches `.git/HEAD` per repo. Gap: the `onBranchChange` callback doesn't propagate through WebSocket to the frontend for active sessions.

Fix:
1. In `server/watcher.ts`, when `BranchWatcher` fires for a session's repo, emit a `session-branch-changed` WebSocket event with `{ sessionId, branch }`.
2. In `server/ws.ts`, broadcast this event to connected clients.
3. In `frontend/src/lib/state/sessions.svelte.ts`, handle the event and update the session's branch field.
4. In `WorkspaceItem.svelte`, the branch name updates reactively. Trigger `CipherText` decode animation on the branch text when it changes.

### Item 3: Inactive repos show stale "default" name

When a workspace/worktree is added but no session is active, read the actual repo name from the git remote URL (`git remote get-url origin`) and the current branch from `.git/HEAD`.

Fix (server-side, in `server/workspaces.ts` or equivalent workspace management module):
1. On workspace add and on server startup, read `git remote get-url origin` to derive the repo name (strip `.git` suffix, use last path segment).
2. Read `.git/HEAD` for the current branch.
3. Store these as defaults in the workspace config object (persisted to `config.json`).
4. If the user has set a custom session name, preserve it (custom name takes precedence).
5. Re-read on reconnect if the workspace has no active session.
6. If `git remote get-url origin` fails (no remote configured), fall back to the directory name of the repo root.

### Item 4: Status indicators redesign

Replace the current StatusDot (single colored circle for everything) with the three-axis indicator model described above. Replace count badges on workspace headers with state-summary pips showing the count per state category.

Workspace header changes from:
```
▼ personal                    [3]
```
To:
```
▼ personal              ◆1 ●1 ─1
```

Each pip uses the same shape+color as the individual session indicator, followed by the count for that state. Pips are ordered by urgency descending (red first, then yellow, then green, then gray). States with zero count are omitted.

### Item 5: PR status icons

Replace colored dots with icon-only PR glyphs using the mapping table above. Icons are bolder and more saturated than current dots. Add tooltip on hover showing the PR state name.

Add comment count badge when GitHub webhook data is available. If not available (no webhook configured), degrade gracefully by omitting the badge.

### Item 6: Sidebar header redesign

Deferred to Phase 3 spotlight design doc (`2026-03-23-relay-phase3-spotlight-identity-design.md`). That doc specifies collapsing the header to `« relay`. This design doc implements whatever that doc decides.

## Generic AgentState Interface

The indicator system must work with any agent, not just Claude Code. The `AgentState` type is already generic:

```typescript
type AgentState =
  | 'initializing'      // agent starting up
  | 'processing'        // agent actively working
  | 'idle'              // agent paused, not waiting
  | 'waiting-for-input' // agent asked a question
  | 'permission-prompt' // agent needs tool approval
  | 'error';            // agent crashed/failed
```

Agent-specific detection maps to this generic type:
- Claude Code: `requiresApproval` -> `permission-prompt`, output streaming -> `processing`
- Codex (future): would map its own states to the same type
- Gemini (future): same pattern

The frontend only cares about `AgentState`. How each agent detects its state is an implementation detail behind this interface.

## Approaches Considered

### Approach A: Truth + Sort (Minimal Viable)
Fix stale data (items 1-3), add attentionScore for sorting, upgrade StatusDot variants. No new UI regions. Ships fast, every change independently valuable.
Effort: M (~2-3 days CC). Completeness: 7/10.

### Approach B: Attention Engine (Ideal Architecture)
Everything in A, plus ephemeral "needs-eyes" rail at sidebar top that promotes items crossing an attention threshold, then decays them back. Full TUI theater treatment.
Effort: L (~4-5 days CC). Completeness: 9/10.

### Approach C: Progressive Attention (Chosen)
Ship A first as foundation, but design the attentionScore API now so B can be added incrementally. Score drives sort order immediately. Needs-eyes rail designed but deferred.
Effort: M-L (~3-4 days CC). Completeness: 8/10.

## Recommended Approach

**Approach C: Progressive Attention.** Ship the truth + sort foundation now. The attention engine evolves from real usage data. You'll know whether sort-alone is enough from actually using it.

## What I noticed about how you think

- You pushed back on the braille spinner placement ("it draws attention to something not actionable") and reframed motion as an attention budget. That's the kind of constraint that produces good design, not just good-looking design.
- "Red like messenger unread notification, not red like error" was a precise emotional distinction that most people wouldn't articulate. You're thinking about what the user FEELS when they see a color, not just what the color MEANS.
- You separated three concerns (state, read/unread, PR status) into independent axes that compose freely. That's systems thinking applied to visual design. Most designers would have made one big status indicator that tries to encode everything.
- The shape progression (organic circle -> angular triangle -> sharp diamond -> blocky square) came from you pushing for a language that works even without color. Accessibility by instinct, not by checklist.

## Responsive & Accessibility

### Mobile (375px)
- **Workspace header pips:** Show max 3 pips. If more states exist, collapse to a single count badge (existing behavior). The 3-pip limit prevents overflow at narrow widths.
- **Indicators:** The tap target is the full session row (44px min height), not the 10-14px indicator. This is correct. No change needed for touch.
- **Tooltips on mobile:** Tooltips require hover, which doesn't exist on touch. On mobile, tapping the indicator area does nothing special (the full row tap navigates to the session). State information is conveyed by the indicator shape/color and the row's bold/normal text treatment. For users who want to learn the indicator meaning on mobile, add a "legend" row in the sidebar footer (a small `?` icon that toggles a legend overlay).
- **Marquee scroll:** Touch devices get the base experience without marquee (per DESIGN.md: "hover interactions are desktop-only enhancements").

### Accessibility
- **Screen reader labels:** Each indicator character gets `aria-label` describing the state and read status. Examples: `aria-label="running"`, `aria-label="needs approval, unread"`, `aria-label="error"`, `aria-label="idle, unread"`.
- **Color-blind support:** The shape system is designed to be distinguishable without color (circle vs triangle vs diamond vs square vs dash). No changes needed, but verify contrast ratios for the stoplight colors against the `#000` background during implementation.
- **Keyboard navigation:** The existing sidebar keyboard navigation (arrow keys through workspace/session items) remains unchanged. The new indicator shapes are purely visual, not interactive targets. Focus styling (`:focus-visible`) on rows is already implemented.
- **Reduced motion:** Per DESIGN.md, all animations respect `prefers-reduced-motion`. The color-alpha pulse and cipher-decode animations should be disabled under this media query. Unread state is still conveyed by bold text (no motion dependency).

## Reviewer Concerns

The following issues were raised during adversarial spec review and not fully resolved:

1. **Worktree HEAD path:** Worktrees use `.git` as a file (not a directory), and their `HEAD` is at `<common-git-dir>/worktrees/<name>/HEAD`. BranchWatcher may need adjustment to handle this. Verify during Item 2 implementation.
2. **State machine diagram ambiguity:** The `needs-answer -> needs-approval -> running` arrow path in the ASCII diagram could be read as sequential rather than parallel. During implementation, treat both `needs-answer` and `needs-approval` as returning directly to `running` on user response.
3. **200ms click delay:** If user testing shows the double-click delay is perceptible, switch to a dedicated collapse affordance (chevron-only click target) and remove the double-click handler.
4. **attentionScore edge case:** A long-running session (100+ minutes) with `running` state drops to score 100 (same as a freshly-seen idle session at 110). This is acceptable — a session running for 100+ minutes without attention is background work by definition.
5. **Webhook integration status for comment badges:** Confirm whether the GitHub webhook handler in the server already provides PR comment data, or whether new infrastructure is required. If new, scope as a separate task.
