## Problem Statement

claude-remote-cli is a remote web interface for managing Claude Code CLI sessions. Users watch agents work in the terminal, then alt-tab to GitHub to review what changed. The current workflow is: agent finishes → push to GitHub → open "changed files" on github.com → leave comments → tell agent to read them back. Every step is friction.

The missing piece: **real-time visibility into what the agent is doing to the codebase**, right next to the terminal. Not another editor, not another review tool. A read-only comprehension layer that renders git state live, with enough intelligence (summaries, syntax highlighting) to build trust in the agent's output without requiring a round-trip to GitHub.

## What Makes This Cool

Your phone becomes a live window into an AI coding agent's work. You see files change in real time as the agent writes code. Each file has a one-line summary of what changed, expandable to a syntax-highlighted diff. You don't need to open VS Code. You don't need to wait for a push to GitHub. You don't need to context-switch at all. The diff grows in front of you while the agent works.

The design principle: **read-only viewport, not another source of truth.** All state lives in git and GitHub. Relay (claude-remote-cli) just makes it visible faster and smarter. Zero local review state, zero commenting system, zero sync problems.

### Server: New Git Functions (server/git.ts)

```typescript
// Returns list of changed files with per-file stats
async function getChangedFiles(
  repoPath: string,
  base?: string, // optional: compare against a branch instead of working tree
  exec: ExecFileAsyncLike = execFileAsync
): Promise<ChangedFile[]>
// Implementation: git status --porcelain=v1 -z (working tree)
//            OR:  git diff --name-status base...HEAD (branch comparison)
// Plus:          git diff --numstat --find-renames (per-file +/- stats)
//
// Merge strategy: status output provides file paths and statuses (M/A/D/R/??).
// numstat output provides per-file additions/deletions keyed by path.
// Join on normalized path (after rename: use new path). For untracked files
// (?? status), derive line count from wc -l since numstat doesn't cover them.

// Returns unified diff for a single file
async function getFileDiff(
  repoPath: string,
  filePath: string,
  base?: string, // omit = working tree, "cached" = staged, branch name = comparison
  exec: ExecFileAsyncLike = execFileAsync
): Promise<string>
// Implementation:
//   base omitted:  git diff --unified=3 --find-renames -- <filePath>
//   base="cached": git diff --cached --unified=3 -- <filePath>
//   base=branch:   git diff branch...HEAD -- <filePath>
//   untracked (?? status): git diff --no-index /dev/null <filePath>
//     (produces a full-addition diff for new files not yet staged)
//
// Error contract: on git failure (detached HEAD, bare repo, not a git repo),
// returns empty string. Caller shows "diff unavailable" inline, not a crash.
```

### Server: New Endpoints (server/workspaces.ts)

```
GET /workspaces/changed-files?path=<repoPath>&base=<ref>
  → { files: ChangedFile[], aggregate: { additions, deletions, fileCount }, error?: string }
  base values: omit (working tree), "cached" (staged), branch name (comparison)
  Errors return { files: [], aggregate: { additions: 0, deletions: 0, fileCount: 0 }, error: "description" }

GET /workspaces/file-diff?path=<repoPath>&file=<filePath>&base=<ref>
  → { diff: string, summary?: string, error?: string }
  Auth: same cookie-token auth as all other routes
```

### Server: Real-Time File Watching (extend server/watcher.ts)

Extends the existing `WorktreeWatcher` in `server/watcher.ts` (not a new module) with git-state change detection. Watches the `.git/` directory (not specific files within it) for each active session's workspace using `fs.watch()`. Watching the directory rather than `.git/index` specifically is more reliable on macOS where FSEvents coalesces rapid writes.

When changes detected:
1. Debounce 500ms (git writes multiple files during operations)
2. Broadcast `files-changed` event via WebSocket with `{ sessionId, workspacePath }`
3. Frontend re-fetches `/changed-files` on receiving event

Note: `.git/` directory watching catches staging, commits, and ref updates. It does NOT fire on working-tree file saves (only when git operations modify `.git/` contents). For working-tree changes between git operations, the frontend also re-fetches on existing `session-activity-changed` events (which fire on every tool-use hook from the agent).

Lifecycle: start watching when a session starts, stop when session ends. Deduplication via `Map<workspacePath, { watcher: FSWatcher, refCount: number }>`. Decrement refCount on session end, close watcher at 0.

Platform note: `fs.watch()` on macOS uses FSEvents (reliable for directory watching). On Linux, `inotify` handles `.git/` non-recursively. New ref files in `.git/refs/` trigger a parent directory event on both platforms.

### Server: Smart Summaries

Two strategies, progressively:

**v1 (ship first):** Parse the diff hunk headers and filenames to generate rule-based summaries:
- "added {functionName}()" when a `+function` or `+async function` line appears
- "modified {N} lines in {functionName}" when changes are within an existing function
- "new file: {description from first non-import line}" for added files
- "deleted file" for removed files
- Fallback: "+{N} -{N} lines"

v2 LLM-powered summaries are a future extension (see Future Extensions section below).

### Frontend: ChangedFiles.svelte

Configuration:

### Frontend: DiffViewer.svelte

Renders unified diff output with syntax highlighting.

**Rendering pipeline (decided):** Use diff2html's JSON output mode (`parse()`) to get a structured array of file diffs with hunks and lines. Then apply Shiki highlighting: iterate the parsed file array, extract code lines into a contiguous string per file, call Shiki's `codeToTokens()` once per file (not per line, for correct multi-line syntax), then re-interleave the tokenized output back into the diff structure for rendering. This is approach (b): diff2html for structure, Shiki for syntax coloring. Using diff2html's JSON output (not its HTML) gives full control over the rendered markup for TUI restyling.

**Shiki placement (decided):** Client-side with lazy-loaded grammars. Shiki grammars are loaded on first diff expansion, then cached in memory. Preload the top 5 grammars (TypeScript, JavaScript, JSON, CSS, Svelte) on app startup to avoid cold-start latency. Other grammars lazy-load on demand. First render of an uncommon language may have ~200-500ms grammar load delay.

Styling:
- TUI theme: zero border-radius, monospace, transparent background (inherits parent), #333 borders
- Line numbers in left gutter, muted (#888888)
- Added lines: green background (rgba(74,222,128,0.08)), green text (--status-success)
- Deleted lines: red background (rgba(248,113,113,0.08)), red text (--status-error)
- Hunk headers in accent color (#d97757)
- Context lines in muted (#888888)
- Max height 400px with overflow scroll

### Frontend: Where Does It Live?

The changed files panel renders as a **collapsible section within the session view**, below the terminal and above the PR top bar. When a session is active:
1. Terminal takes primary space
2. Changed files panel sits below, initially collapsed to just the aggregate stats bar ("7 files, +142 -38")
3. Click to expand the full file list
4. Click a file to expand its diff inline

On mobile: the panel is a separate tab/view accessible via a bottom nav or swipe.

### Diff Sources

The panel supports multiple diff contexts via the `base` parameter:
1. **Working tree** (default): `git diff` — what the agent is changing right now
2. **Staged changes**: `git diff --cached` — what's staged for commit
3. **Branch comparison**: `git diff main...HEAD` — total diff for the branch
4. **PR diff**: prefer local `git diff base...head` when the local repo has both refs fetched. Fall back to GitHub REST (`gh api repos/{owner}/{repo}/pulls/{number}/files`) when the base ref is not available locally. Also add `files(first:100)` to `buildPrSearchQuery` for file-level stats (but not full diffs, since GitHub's GraphQL `patch` field is truncated for large files).

A simple toggle in the top bar switches between these. Default is "working tree" during active sessions, "branch comparison" otherwise.

## Phase 3 Design: Diff Viewer (Standalone)

Phase 2's inline DiffViewer handles 90% of the diff viewing use case. Phase 3 adds:

### Full-page diff mode
Click "expand" on any file diff to open a full-page view with:
- Side-by-side mode toggle (unified is default, side-by-side for wide screens)
- File navigation sidebar (reuses ChangedFiles.svelte in a narrow layout variant, not a new component)
- Keyboard shortcuts: `j/k` to navigate between files, `n/p` to jump between hunks
- URL-addressable: `/diff?path=...&file=...&base=...` (subject to same cookie-token auth as all routes)

### PR diff integration
For sessions with an active PR, add a "PR diff" tab that shows the full PR's changed files using GitHub GraphQL data. This avoids needing to go to github.com for the common "what does this PR contain?" question.

### Performance for large diffs
- Virtualized rendering: only render visible lines (use intersection observer)
- Truncate diffs over 5000 lines with "show more" button
- File-level lazy loading: fetch individual file diffs on expand, not all at once

### Launch Mechanism (server/workspaces.ts)
```
POST /workspaces/open-in-editor
  { editor: "code", path: "/path/to/repo", file?: "server/git.ts", line?: 42 }
  → spawns: code --goto /path/to/repo/server/git.ts:42
```

Security: only allows launching pre-detected editors. No arbitrary command execution. The path must be within a registered workspace.

## Shared Infrastructure

### Syntax Highlighting Strategy
**Shiki** (shiki.style) for token-level syntax highlighting:
- Same engine as VS Code — consistent, high-quality
- Supports all languages via TextMate grammars
- Runs client-side with lazy-loaded grammars (decided in DiffViewer spec above)
- Preload top 5 grammars on app startup: TypeScript, JavaScript, JSON, CSS, Svelte
- One dependency, well-maintained (31k+ GitHub stars)

TUI restyling: create a custom Shiki theme matching DESIGN.md colors:
- Background: transparent (inherit from parent)
- Keywords: #c792ea (purple, matching the wireframe)
- Functions: #82aaff (blue)
- Strings: #c3e88d (green)
- Types: #ffcb6b (yellow)
- Comments: #888888 (muted)

### diff2html for Diff Parsing
**diff2html** (diff2html.xyz) for unified diff → HTML:
- Parses `git diff` output into structured data
- Generates HTML for both unified and side-by-side views
- File rename detection
- Integration: use diff2html's `parse()` for JSON output, then render custom HTML with Shiki-highlighted content lines (decided in DiffViewer spec above)

### File Rendering Component (shared)
A `CodeBlock.svelte` component wrapping Shiki:
- Input: `{ code: string, language: string, theme?: string }`
- Output: syntax-highlighted HTML with line numbers
- Reusable across: DiffViewer (diff lines), file preview (full file), future features

## Constraints

1. **Read-only viewport** — no local review state, no comments, no approvals. All review state lives in git/GitHub.
2. **TUI aesthetic** — monospace everywhere, zero border-radius, DESIGN.md colors, cipher-decode loading states.
3. **Progressive disclosure** — summary first, expand to diff. Don't overwhelm with full diffs on load.
4. **Mobile-friendly** — card layout on small screens, touch-friendly 44px min tap targets.
5. **No new databases/state stores** — everything derived from git CLI and GitHub GraphQL.
6. **Existing module pattern** — new server functions follow the injectable exec pattern from `server/git.ts`.

## Premises

1. Real-time watching (fs.watch on .git/) > on-demand refresh
2. Read-only viewport, no local review state (everything in git/GitHub)
3. Phase 2 (changed files) is higher priority than Phase 1 completion (file browser)
4. Both syntax-highlighted diffs AND smart summaries — progressive trust model
5. "Open in editor" (Phase 4) is low priority
6. Existing Express + WebSocket + git CLI architecture is sufficient

## Approaches Considered

### Approach A: Changed Files Panel (Minimal)
Raw file list + unified diff, poll-based, no syntax highlighting, no summaries. Ships in 1-2 days. Completeness: 5/10.

### Approach B: Smart Viewport (Chosen)
File list + diff2html + Shiki syntax highlighting + auto-generated summaries + real-time via fs.watch. Progressive disclosure from summary to full diff. 3-5 days. Completeness: 8/10.

### Approach C: Agent Flight Recorder (Deferred)
Everything in B plus a timeline correlating file changes with tool-use events. 5-8 days. Completeness: 10/10. Deferred to Phase 2.5.

## Recommended Approach

**Approach B: Smart Viewport.** Delivers the trust-verification flow (syntax highlighting for catching hallucinations) and the quick-comprehension flow (auto-generated summaries) without the scope risk of the flight recorder. The flight recorder is a natural extension once B ships, using the same event infrastructure.

## Future Extensions

### Phase 2.5: Agent Flight Recorder
Correlate file changes with agent tool-use events to create a causal timeline. "While the agent was running Edit tool on auth.ts, +15 -3 lines changed." Requires snapshotting `git diff --numstat` on each `tool-result` hook event. Uses existing hooks infrastructure (`server/hooks.ts`, `server/ws.ts`).

### v2 LLM-Powered Summaries
If a Claude session is active, pipe the diff through a lightweight LLM call to generate per-file summaries. Batch all changed files into one call. Cache aggressively (invalidate on next `files-changed` event). Gated behind a user preference in settings. Only pursue after rule-based v1 summaries prove insufficient.
