## Problem Statement

Relay's command palette (Spotlight) has 3 registered commands out of 100+ user-facing actions. There is no command registry, no centralized shortcut system, and features drift away from the palette with every new addition. The result: power users hit Cmd+P and see a search box that knows about worktrees, sessions, and PRs, but can't do most of the things the app can do. On mobile, there is no command palette trigger at all.

This is a 4-phase epic: audit the gap, build a registration architecture, fix keyboard shortcuts, and add discoverability features. The design absorbs the existing `tooltip-and-keyboard-shortcuts-design.md` (2026-03-27) which covered phases 3-4 partially.

## What Makes This Cool

Every action reachable from any screen. Context-aware: it surfaces the right commands for what you're looking at. Frecency-ranked: it gets faster as you use it. On mobile, one tap away via `> command` bar. On desktop, Cmd+P. The palette is the control surface. (North star vision in the Appendix.)

## Constraints

- Svelte 5 runes (no stores, no classes for state)
- All lowercase, no emoji, TUI aesthetic (per DESIGN.md)
- Mobile-first: command palette must work on phones/tablets with no keyboard
- npm package distribution: no server-side changes for the palette itself
- Must not break existing Spotlight functionality during migration
- The tooltip-and-keyboard-shortcuts design doc is absorbed into this design
- Natural language and composable workflows are explicitly out of scope for phases 2-4
- CommandPalette.svelte must preserve Spotlight.svelte's existing ARIA roles (role="dialog", aria-modal, role="listbox", role="option", aria-activedescendant)

## Premises

1. The command palette is the primary control surface — not menus, not sidebar, not context menus alone.
2. Total coverage comes first, composable workflows come later.
3. This design absorbs the tooltip-and-keyboard-shortcuts design doc.
4. Command registration must be co-located with features, not centralized in one file.
5. Natural language + composable workflows are the north star but not in the initial implementation phases.
6. Mobile needs a dedicated, always-visible palette trigger — can't rely on Cmd+P.
7. Registration must be testable/verifiable — a coverage test that fails when new actions aren't registered.

## Cross-Model Perspective

Codex (GPT-5.4) provided an independent cold read:

**Coolest version:** "An action OS for Relay. Every user-facing capability becomes a typed action with one canonical definition. The palette, tooltips, context menus, mobile action sheet, onboarding, and later NL/workflow features are all just views over that same action graph. The killer addition: after a user performs the same 3-step flow a few times, Relay offers 'save as workflow' and turns it into a named reusable command."

**Key insight:** "They are not actually excited by a nicer search box. They are excited by Relay becoming operable, teachable, and eventually programmable."

**50% reference:** VS Code's command contribution model is the right backbone. The 50% to build: co-located Svelte registration, frecency, context awareness around workspace/session/agent state, mobile-first invocation, coverage enforcement, workflow composition.

**Weekend build priority:** "Build the substrate, not the dream. defineAction() and a registry. One action type. One ID namespace. One shortcut format. One when() contract. One handler shape."

## Approaches Considered

### Approach A: Registry-First Overhaul

Build `defineAction()` + `ActionRegistry` as the single source of truth. All commands, shortcuts, and context rules live in one typed system. Spotlight reads from the registry. Tests enforce coverage.

- **Effort:** M
- **Risk:** Low (incremental, existing Spotlight keeps working during migration)
- **Pros:** Single canonical definition, coverage tests prevent drift, co-located with features
- **Cons:** Initial infrastructure overhead, must migrate existing commands, full coverage is a grind

### Approach B: Incremental Spotlight Enhancement

Keep Spotlight.svelte as-is. Add commands to the existing hardcoded array one-by-one. Add frecency via localStorage. Add mobile trigger. No new architecture.

- **Effort:** S
- **Risk:** Medium (no enforcement = drift continues)
- **Pros:** Fastest visible improvement, no architecture overhead
- **Cons:** Doesn't solve root cause, no path to composability, shortcuts remain scattered

### Approach C: Action OS — Full Graph Architecture

Codex's "action OS" vision. Every action is a typed node in an action graph with context predicates, composability metadata, telemetry hooks, and mobile presentation hints. Includes workflow recording.

- **Effort:** L-XL
- **Risk:** High (scope creep, over-engineering before coverage is proven)
- **Pros:** Most complete long-term architecture, directly enables NL/composable north star
- **Cons:** Delayed shipping, workflow recording is complex, infrastructure nobody uses yet

## Recommended Approach

**Approach A with C's north star.** Build the registry infrastructure now. Design the action type to be forward-compatible with composability metadata, context predicates, and workflow hooks — but don't implement those features yet. The action type has optional fields for the future; the initial phases only use the core fields.

### Action Type Definition

```typescript
// frontend/src/lib/actions/types.ts

type ActionView = 'workspace' | 'session' | 'dashboard' | 'settings' | 'org';

type ActionContext = {
  /** Current view, derived by priority: dialog open > session active > workspace active > org */
  view: ActionView;
  /** Active workspace ID, if any */
  workspaceId?: string;
  /** Active session ID, if any */
  sessionId?: string;
  /** Whether an agent is currently running */
  agentRunning?: boolean;
  /** Whether we're on mobile */
  isMobile?: boolean;
  /** Current PR state, if applicable */
  prState?: 'none' | 'draft' | 'open' | 'merged' | 'closed';
};

type Action = {
  /** Unique identifier: 'category.verb-noun' e.g. 'session.new-agent' */
  id: string;
  /** Display label — all lowercase per DESIGN.md */
  label: string;
  /** Short description for palette search */
  description?: string;
  /** Search aliases (alternative terms users might type) */
  aliases?: string[];
  /** Category for grouping in palette */
  category: 'session' | 'workspace' | 'pr' | 'settings' | 'navigation' | 'terminal';
  /** Icon character or icon component reference */
  icon?: string;
  /** Keyboard shortcut definition */
  shortcut?: {
    /** Key combo e.g. 'mod+t' where mod = Cmd on mac, Ctrl elsewhere */
    key: string;
    /** Whether shortcut works when an input is focused */
    global?: boolean;
  };
  /** Context predicate: when is this action available? */
  when?: (ctx: ActionContext) => boolean;
  /** Handler: what happens when executed */
  handler: (ctx: ActionContext) => void | Promise<void>;
  /** Mobile presentation hint */
  mobile?: {
    /** Whether to show in mobile action sheet */
    showInSheet?: boolean;
    /** Mobile-specific label (shorter) */
    label?: string;
  };

  // --- North star fields (optional, for future phases) ---

  /** Composability: can this action be chained? */
  composable?: boolean;
  /** Tags for NL matching */
  tags?: string[];
  /** Telemetry: track usage for frecency */
  trackUsage?: boolean;
};
```

### Registry Architecture

```
frontend/src/lib/actions/
  types.ts            — Action type definition
  registry.svelte.ts  — ActionRegistry (Svelte 5 runes-based)
  frecency.ts         — Frecency scoring using localStorage
  shortcuts.svelte.ts — Keyboard shortcut listener (replaces scattered listeners)
  context.svelte.ts   — ActionContext provider (derives current context from app state)

frontend/src/lib/actions/definitions/
  session.ts          — Session actions (new-agent, new-terminal, close, switch tab)
  workspace.ts        — Workspace actions (add, settings, navigate)
  pr.ts               — PR/branch actions (create, push, rename, switch)
  settings.ts         — Settings actions (toggle YOLO, connect GitHub, etc.)
  navigation.ts       — Navigation actions (go to dashboard, switch view)
  terminal.ts         — Terminal actions (zoom, scroll, paste)
```

Each definition file exports an array of Action objects. Components import and register them using `$effect` for proper lifecycle management.

### Co-located Registration Pattern

**Definition files export metadata only — no handlers.** Handlers live in App.svelte (which owns most action flows), not in leaf components.

```typescript
// frontend/src/lib/actions/definitions/session.ts
// Exports metadata WITHOUT handlers

export type ActionMeta = Omit<Action, 'handler'>;

export const sessionNewAgent: ActionMeta = {
  id: 'session.new-agent',
  label: 'new agent session',
  description: 'start claude or codex',
  category: 'session',
  icon: '+',
  shortcut: { key: 'mod+t', global: true },
};

export const sessionClose: ActionMeta = {
  id: 'session.close',
  label: 'close active session',
  category: 'session',
  icon: '×',
  shortcut: { key: 'mod+w' },
};
```

**Registration is centralized in App.svelte.** This matches reality: App.svelte already owns `handleQuickAgent()`, `handleNewWorktree()`, `handleOpenSettings()`, session close, tab switching, and most other orchestration. Fighting this by distributing registration to leaf components (which just call UP to App.svelte via callbacks) adds ceremony without benefit.

```svelte
<!-- App.svelte — registers ALL global actions on mount -->
<script>
  import { registerGlobal } from '$lib/actions/registry.svelte';
  import { sessionNewAgent, sessionClose } from '$lib/actions/definitions/session';
  import { workspaceAdd } from '$lib/actions/definitions/workspace';
  // ... import all action metadata

  // Build full Action objects by spreading metadata + handler closures
  const globalActions = [
    { ...sessionNewAgent, handler: () => handleQuickAgent() },
    { ...sessionClose, handler: () => closeActiveSession() },
    { ...workspaceAdd, handler: () => { addWorkspaceDialogOpen = true; } },
    // ... all 15 HIGH-priority actions in Phase 2
  ];

  registerGlobal(globalActions); // registered once, never unregistered (App is always mounted)
</script>
```

**Global vs contextual distinction:**
- `registerGlobal()`: called once by App.svelte on mount. These actions are always available (gated by `when()` predicates, not by component lifecycle). Never unregistered.
- `registerContextual()` / `unregisterContextual()`: for the rare case where an action only makes sense while a specific component is mounted (e.g., a future Phase 5 dialog-specific action). Uses `$effect` with cleanup. NOT needed for Phase 2-4 since all 15 HIGH-priority actions are global.

This pattern ensures:
1. Definition files are pure data (importable, testable, no side effects)
2. Handlers close over App.svelte's state and functions (where they already live)
3. No lifecycle dance for global actions
4. Contextual registration available for future phases if needed

For actions that depend on component state (like "close active session" needing to know which session is active), the handler receives the `ActionContext` which includes the active session ID. The handler then calls the same function the button's onclick calls.

### ActionContext Derivation

The `context.svelte.ts` module derives `ActionContext` from existing state modules:

```typescript
// frontend/src/lib/actions/context.svelte.ts

// View derivation priority (highest wins):
// 1. SettingsDialog open → 'settings'
// 2. Active session ID set → 'session'
// 3. Active workspace path set → 'workspace'
// 4. Org dashboard visible → 'org'
// 5. Fallback → 'dashboard'

// Source state modules:
// - view: derived from ui.svelte (dialog state) + sessions.svelte (activeSessionId) + ui.svelte (activeWorkspacePath)
// - workspaceId: from ui.svelte activeWorkspacePath
// - sessionId: from sessions.svelte activeSessionId
// - agentRunning: from sessions.svelte session.status
// - isMobile: from ui.svelte isMobile (existing)
// - prState: from svelte-query PR data for the active workspace's branch
```

**Phase 2 note:** Phase 2 implements BASIC context gating, not the full ActionContext infrastructure. Each HIGH-priority action gets a simple `when()` predicate using three boolean flags: `hasWorkspace` (active workspace selected), `hasSession` (active session tab open), `hasPr` (active branch has a PR). Actions that can't execute in the current context are hidden from the palette.

Basic Phase 2 gating for the 15 HIGH-priority actions:

| Action | when() | Rationale |
|--------|--------|-----------|
| Add workspace | always | global |
| New terminal session | hasWorkspace | needs a workspace |
| New agent session | hasWorkspace | needs a workspace |
| New worktree | hasWorkspace | needs a workspace |
| Open settings | always | global |
| Create PR | hasWorkspace && !hasPr | only if no existing PR |
| Push branch | hasWorkspace | needs a workspace |
| Start session on repo | hasWorkspace | needs a workspace |
| Start work on ticket | hasWorkspace | needs a workspace |
| Connect GitHub | always | global |
| Close active session | hasSession | needs an active session |
| Toggle YOLO mode | always | global toggle |
| Check for updates | always | global |
| Kill session | hasSession | needs an active session |
| Switch branch | hasWorkspace | needs a workspace |

The full `ActionContext` derivation (view priority, agentRunning, prState) is still Phase 4. Phase 2's gating is just 3 reactive booleans derived from existing state.

### Coverage Enforcement

A test file `test/action-coverage.test.ts` with two layers:

**Layer 1 — Registry validation (CI-blocking):**
1. All registered action IDs are unique (no duplicates)
2. All required Action fields are present and well-formed
3. No conflicting keyboard shortcuts (same key combo, overlapping context)
4. A manually maintained allowlist of all 71 palettable actions from the Phase 1 audit (57 gap actions + 14 existing registrations being migrated to the registry) all have corresponding registered IDs

**Layer 2 — Gap detection (non-blocking, audit helper):**
A script that walks `.svelte` files for interactive elements (`onclick`, `<button>`, `role="button"`) and flags potential unregistered actions for human review. This is a development aid, not a CI gate, because distinguishing "user-facing actions that should be registered" from "structural UI interactions" (backdrop clicks, category headers) requires judgment.

The allowlist approach is the enforcement mechanism: when a developer adds a new user-facing action, they must add its ID to both the action registry AND the allowlist. The CI test cross-references them. Forgetting either one fails the build.

### Mobile Entrypoint

**Trigger:** A persistent search/command icon in `MobileHeader.svelte` (replacing or augmenting the current hamburger menu). One tap opens the palette.

**Presentation:** On mobile, the palette renders as a bottom sheet (not a centered dialog) with:
- Full-width search input at top with large touch target
- Category tabs below search: all, sessions, workspaces, PRs, settings (maps to Action.category values; navigation and terminal categories are folded into "all")
- Results as large touch-friendly rows (min 48px tap targets)
- Swipe down to dismiss

**Long-press power shortcut:** Long-pressing the header bar (500ms) opens the palette with the cursor already in the search field. Same as the sidebar's existing long-press-to-drag pattern.

### Spotlight Migration Path

**Phase 2:** Modify `Spotlight.svelte` to read commands from ActionRegistry instead of its hardcoded array. Spotlight keeps its existing search/resources UI. This is a refactor of the data source, not a component rewrite.

**Phase 3:** Build new `CommandPalette.svelte` alongside Spotlight. CommandPalette adds mobile bottom sheet, category tabs, and shortcut hints. Existing Spotlight search (workspaces, sessions, PRs, issues) becomes a "resources" section in CommandPalette.

**Phase 3 end:** Swap Spotlight for CommandPalette in App.svelte. Delete Spotlight.svelte.

This means Phase 2 ships with the existing Spotlight UI backed by the new registry, and Phase 3 ships the new CommandPalette component.

### Frecency Implementation

```typescript
// frontend/src/lib/actions/frecency.ts

type UsageRecord = {
  id: string;
  count: number;
  lastUsed: number; // timestamp
};

// Score = frequency * recency_decay
// recency_decay = 1 / (1 + hours_since_last_use / 24)
// Stored in localStorage under 'relay:action-frecency'
```

The palette's default sort order (when no query is typed) is:
1. Recently used actions (frecency-ranked)
2. Contextual actions (matching current view)
3. All other actions (alphabetical within categories)

When a query is typed, fuzzy match score is weighted by frecency.

### Shortcut Registry

The scattered keyboard listeners in App.svelte are replaced by a `ShortcutListener` that reads from the ActionRegistry. **Terminal.svelte's shortcuts (zoom, paste) stay in xterm's custom key handler** — xterm intercepts keys before they reach the document, and moving those to a document-level listener would cause double-handling. ShortcutListener only manages non-terminal shortcuts.

```typescript
// frontend/src/lib/actions/shortcuts.svelte.ts

// On mount: iterate all registered actions with shortcuts
// Create a single keydown listener that matches against the registry
// Handle platform detection (mod = Cmd on mac, Ctrl elsewhere)
// Handle 'global' flag (whether to fire when input is focused)
// Shortcut scope resolution: the when() predicate is the scoping mechanism.
// Two actions can share a shortcut if their when() predicates are mutually exclusive
// (e.g., one fires only in 'session' view, the other only in 'settings' view).
// If when() predicates overlap, last-registered wins with console.warn in dev.
```

### Inline Shortcut Hints

Buttons and menu items that have a corresponding registered action show the keyboard shortcut inline. A helper component:

```svelte
<!-- ShortcutHint.svelte -->
<script>
  let { actionId } = $props();
  // Looks up the action in the registry, renders the shortcut badge
</script>

{#if shortcut}
  <kbd class="shortcut-hint">{formattedShortcut}</kbd>
{/if}
```

This replaces the tooltip-and-keyboard-shortcuts design doc's "TooltipProvider" concept with a simpler, registry-backed approach.

## Integration with Tooltip-and-Keyboard-Shortcuts Design

The `2026-03-27-tooltip-and-keyboard-shortcuts-design.md` proposed:
- A `ShortcutRegistry` class — **superseded** by ActionRegistry (shortcuts are a field on Action, not a separate registry)
- A `TooltipProvider` component — **superseded** by ShortcutHint (simpler, registry-backed)
- A `Tooltip` component — **retained** as a visual primitive, but shortcut data comes from ActionRegistry

The tooltip component itself (visual rendering of hover hints) is still useful. But the shortcut data source and registration pattern from that design doc are fully absorbed into this Command Center architecture.

## Open Questions

1. **Should shortcuts be user-customizable?** VS Code allows rebinding. This adds complexity (settings storage, conflict resolution UI). Recommend: not in initial phases, but the registry design should make it possible by separating default shortcuts from user overrides.

2. **How does the palette interact with tmux copy mode?** When copy mode is active, should the palette still be openable? Probably yes, since Cmd+P doesn't conflict with tmux bindings.

3. **Should the coverage test be a lint rule or a test?** Lint rule catches it at dev time. Test catches it in CI. Recommend: test first (simpler), lint rule later if test isn't sufficient.

4. **What about actions that require parameters?** "Switch to tab N" needs a tab number. "Rename session" needs input. The palette could support inline parameter input (like VS Code's "Go to Line: ___") as a future enhancement. For now, parameterized actions open their respective dialogs.

5. **Frecency storage migration.** If we switch from the current hardcoded spotlight to a registry-backed palette, do we carry over any usage data? Probably not worth it — let frecency rebuild naturally.

## Success Criteria

- Every user-facing action in the app is accessible from the command palette
- Keyboard shortcuts are discoverable (shown inline on buttons, listed in palette)
- Mobile users can open the palette in one tap and execute any action
- New features that add UI actions without registering them fail the CI build
- Frecency ranking makes the palette faster to use over time
- The existing tooltip-and-keyboard-shortcuts design doc is fully superseded
- The action type is forward-compatible with composable workflows

## Appendix: Future Vision — Action OS

This section describes the long-term north star. It is NOT in scope for phases 2-4.

The command palette evolves into a programmable action surface:
- **Natural language commands:** Type "create a PR for this branch" in the palette and it maps to the right action via NL matching against `tags` and `aliases`.
- **Composable workflows:** Chain commands: "new worktree + start agent + YOLO mode" as a single compound action.
- **Workflow recording:** After a user performs the same 3-step flow a few times, Relay offers "save as workflow" and turns it into a named reusable command.
- **User-teachable:** Users can edit saved workflows, share them, and the palette learns from usage patterns.

This is the moment Relay stops being "a web UI for Claude/Codex" and becomes a programmable control plane for agent orchestration. The Phase 2-4 architecture (action type with optional `composable`, `tags` fields) is designed to make this possible without a rewrite.
